# Audit skalabilitas frontend (web + mobile)

Tanggal: 2026-10-10. Pertanyaan: apakah aplikasi tetap lancar saat data tumbuh (ribuan siswa, 160 ribu+ baris presensi per semester, 13 ribu+ pinjaman, banyak notifikasi). Audit ini melengkapi `docs/16-audit-performa-web.md` (bundle, animasi, N+1 promosi, memo baris presensi, dan seterusnya) dan tidak mengulanginya. Metode: audit statis kode `apps/web`, `packages/ui`, `apps/mobile`. Tidak ada pengukuran runtime.

Catatan lingkup: hook `useActionInboxCount` (`features/inbox/use-action-inbox-count.ts`) belum ada di cabang ini (dikerjakan agen lain). Penilaian polling-nya ada di bagian "Polling" berdasarkan deskripsi tugas, bukan pembacaan kode.

## Pola dasar yang perlu dipahami

1. **API daftar tidak punya total.** Respons daftar hanya `{ data }` (contoh `listDirectoryUsers`, `listLibraryMembers` di `packages/api-client/src/gen/schema.d.ts`). Akibatnya paginasi harus prev/next (offset atau cursor), bukan nomor halaman. `users-view` adalah template yang benar (`mode="cursor"` + `UsersCursorPagination`).
2. **`useDirectoryQuery` adalah lookup id ke nama, bukan picker.** `features/reference/api.ts:113-126` mengambil sampai `limit: 5000` pengguna per `profile_kind`, di-cache satu kali per sesi (`staleTime` referensi), dan dipakai di sekitar 50 layar. Untuk lookup ini wajar; ia menjadi masalah di dua hal: (a) payload besar saat pertama dibuka (5.000 siswa kira-kira ratusan kB JSON dan satu kali `Map`), (b) plafon 5.000 membuat siswa di atas angka itu tampil "tidak dikenal".
3. **Fake paginasi `pageSize: 200`.** Beberapa layar memanggil API dengan `limit: 200` lalu memberi `DataTable` `pagination={{ pageIndex: 0, pageSize: 200 }}` dengan `onPaginationChange={() => undefined}`. Baris ke-201 dan seterusnya tidak pernah terlihat, tanpa pesan apa pun.

### Yang sudah benar (jangan diubah)

- Library berat: `exceljs` hanya diimpor sebagai type di `features/school/lib/user-import.ts:5` dan dimuat dinamis; tidak ada pdf/chart pihak ketiga (grafik dibuat sendiri: `dashboard-series-chart`, `login-activity-chart`, `risk-reasons-chart`). Tidak ada temuan bundle baru.
- `users-view` (cursor), `homeroom-view`, `promotion-view` (50 baris per halaman), laporan harian/bulanan presensi: server-side atau terbatas.
- Hitung notifikasi belum dibaca sudah memakai endpoint khusus `GET /v1/notifications/unread-count` (`notifications/api.ts:55-62`), 60 dtk, berhenti saat tab tersembunyi.

- 160 ribu baris presensi per semester tidak pernah dimuat sekaligus di klien: tampilan sesi hanya memuat roster satu sesi; laporan berpaginasi dari server.

Penilaian: biaya per pengguna kecil, tetapi tidak berbanding terbalik dengan data; yang tumbuh adalah jumlah pengguna serentak. Sekolah 5.000 siswa + 300 staf, jam sibuk pagi: 300 sesi staf x (~6 polling per menit) = ~30 request/dtk hanya dari polling. Rekomendasi:

1. **Hitung inbox lewat satu endpoint ringkas.** `useActionInboxCount` memonitor beberapa antrean setiap 30-60 dtk dan menarik sampai 200 kandidat SP hanya untuk menghitung. Buat `GET /v1/inbox/counts` (satu round trip, angka saja, dihitung di SQL dengan `COUNT(*)`) dan pakai satu query dengan interval >= 60 dtk. Jangan pernah mengambil daftar 200 baris untuk badge.
2. **Pastikan setiap polling punya `refetchIntervalInBackground: false`.** Yang belum: `stocktake-api.ts:55`, `monitor-view.tsx:108` / `monitor/api.ts:33` (monitor layar kiosk mungkin memang harus jalan di latar; kalau iya, tulis eksplisit dengan komentar).
3. **Gunakan websocket yang ada untuk invalidasi**, bukan polling berdampingan: saat event `notification`, `permit`, `attendance` datang, panggil `queryClient.invalidateQueries` untuk key terkait, lalu naikkan interval polling menjadi 5 menit sebagai jaring pengaman.
4. **Jitter** 0-20% pada interval agar 300 klien yang dibuka bersamaan (bel masuk) tidak serempak menembak API di detik yang sama.

## Rendering mahal dan query key

- Tidak ditemukan query key yang berubah tiap render pada jalur yang diaudit. `useLibraryMembersQuery` menyusun key dengan string gabungan `limit:offset:search` yang stabil (`members-api.ts:89-93`).
- `DataTable` merender tabel dan kartu sekaligus (`docs/16` temuan 12): untuk daftar 50 baris biayanya konstan 2x; menjadi masalah hanya jika `pageSize` dinaikkan, itu alasan lain menolak pola `pageSize: 200` (poin 3-5).
- Virtualisasi: tidak ada daftar yang merender ratusan baris sekaligus setelah perbaikan paginasi (maks 50 per halaman, roster presensi satu sesi sekitar 36). Tidak ada dependensi virtualisasi di repo; menambahkannya tidak dibenarkan oleh data saat ini. Jika nanti ada layar yang butuh 500+ baris dalam satu tampilan (mis. matriks presensi bulanan), pakai `@tanstack/react-virtual` (satu dependensi kecil, sejalan dengan `@tanstack/react-table` yang sudah dipakai).

## Perbaikan yang dilakukan

1. `features/reference/components/directory-picker.tsx` (baru) dengan test: picker pencarian server untuk siswa/guru/staf, debounce 300 ms, maksimum 50 hasil, label terpilih dipertahankan.
2. `features/billing/components/payment-desk-view.tsx`: memakai `DirectoryPicker`; tidak lagi memuat seluruh direktori siswa di layar kasir.
3. `features/library/components/members-view.tsx`: paginasi offset 50 per halaman dengan Sebelumnya/Berikutnya, hilang pemotongan diam-diam di 200; pencarian murni server (`mode="cursor"`); test paginasi. String i18n `pagePrev`/`pageNext` ditambahkan di `messages/features/library.{id,en}.json`.
